### 一、问题描述与优化建议

- **【高】[FusionAlgoInstanceServiceImpl.java:约677行] 同步落盘分支返回错误的 resultId**  
  - **问题描述**：同步落盘逻辑中，`persistTask.run()` 执行后直接返回 `finalExistingId != null ? finalExistingId : 0L`。当 `existingId` 为 `null` 且实际执行了 `storageProvider.saveResult(...)` 创建新记录时，方法返回 `0L` 而不是真实的 `resultId`。  
  - **关键代码**：
    ```java
    persistTask.run(); // 单任务同步落盘回退，保证记录 ID 完整返回
    return finalExistingId != null ? finalExistingId : 0L;
    ```
  - **影响**：调用方依赖返回的 `resultId` 进行后续处理（如关联业务、审计追踪、幂等控制），获得 `0L` 将导致数据链路断裂或业务逻辑错误。  
  - **建议**：同步分支应返回 `persistTask` 内部实际计算出的 `resultId`，例如将 `resultId` 提升为 `final` 包裹类型或返回值；或者重构方法，从 `persistTask` 中取出真实 ID 再返回。

- **【高】[FusionAlgoInstanceServiceImpl.java:约674行] 异步落盘直接返回 0L 且异常仅记录日志**  
  - **问题描述**：批量调度模式（`preloadedVersion != null` 或线程名以 `fusion-batch-` 开头）下，将落盘任务提交到 `batchExecutor` 后立即返回 `0L`，不再等待执行结果。当落盘失败时，`catch` 块仅记录错误日志，调用方无法感知失败。  
  - **关键代码**：
    ```java
    if (preloadedVersion != null || Thread.currentThread().getName().startsWith("fusion-batch-")) {
        CompletableFuture.runAsync(persistTask, batchExecutor);
        return 0L; // 批量模式异步落盘，立即释放 Worker 线程
    }
    ```
    ```java
    catch (Exception e) {
        log.error("【算法结果落盘失败】实例: {} (ID: {}), 任务: {}, 错误: {}",
                instance.getInstanceName(), instanceId, taskName, e.getMessage(), e);
    }
    ```
  - **影响**：调用方误认为落盘成功（返回值 0L 可能被解释为成功），实际数据可能未写入数据库或事件未发布，造成数据丢失或下游业务静默失败。  
  - **建议**：异步落盘应返回 `CompletableFuture<Long>` 供调用方决策，或至少抛出异常/返回失败状态；不建议在无法确认成功时返回成功码。若必须异步释放线程，应通过事件或回调机制通知失败。

- **【中】[FusionAlgoContextLoader.java:putOrUpdateTimeSeriesResult方法] 并发合并大列表存在性能瓶颈与复制开销**  
  - **问题描述**：在 `ConcurrentHashMap.compute` 中对每个 key 进行 `new ArrayList<>(existing.size() + timeSeries.size())` 并复制两个列表。当 `timeSeries` 规模较大（如数万条时序数据）且高并发时，频繁的内存分配与复制会引发 GC 压力。  
  - **关键代码**：
    ```java
    List<FusionTimeSeriesDTO> merged = new ArrayList<>(existing.size() + timeSeries.size());
    merged.addAll(existing);
    merged.addAll(timeSeries);
    return merged;
    ```
  - **影响**：在高并发加载大数据量场景下，线程竞争与列表复制可能成为性能瓶颈。  
  - **建议**：评估是否必须进行物理合并，可考虑使用分段容器或延迟合并；若需保持列表不可变，可尝试批量追加后再生成最终列表。

- **【中】[TradingPriceMockSupplier.java:约73行] 日期字符串截取未校验长度**  
  - **问题描述**：`targetDateStr = timeVal.getValue().toString().substring(0, 10);` 假设时间字符串长度至少 10，若传入格式非预期（如仅时间、无日期部分），将抛出 `StringIndexOutOfBoundsException`，异常被外层捕获后 `targetDateStr` 保持 `null`，导致电价数据装配被静默跳过。  
  - **关键代码**：
    ```java
    targetDateStr = timeVal.getValue().toString().substring(0, 10);
    ```
  - **影响**：目标日期解析失败时，交易算子的前置电价数据缺失，影响算法计算结果正确性。  
  - **建议**：使用日期解析工具（如 `DateUtil.parse`）或先校验长度/格式，避免直接截取；对无法识别的格式给出明确告警。

- **【中】[JsTdbDataSourceStrategy.java:约369行] 日志直接输出集合存在 NPE 风险且可能造成日志膨胀**  
  - **问题描述**：日志语句中直接调用 `queryKeys.size()` 并打印 `queryKeys` 集合，未进行判空。若 `queryKeys` 为 `null`，将触发 `NullPointerException`；若集合很大，日志输出会占用大量磁盘与网络资源。  
  - **关键代码**：
    ```java
    log.info("📢【纯极生 TDBAPI.select 测试】#{} | 表: {} | kids点位({}): {} | 纯极生物理耗时: {} ms | 返回数据记录行数(docs): {}",
             currentCount, tableName, queryKeys.size(), queryKeys, selectTime, totalDocCount);
    ```
  - **影响**：可能导致日志打印失败或服务因日志量过大而性能下降。  
  - **建议**：先判空，并限制日志内容长度或只输出集合大小，避免直接打印整个集合。
